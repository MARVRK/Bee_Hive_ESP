# Система удалённого мониторинга пасечного улья — Bee Hive V2

---

## 1. Общее описание проекта

Разработка автономного IoT-устройства для круглосуточного мониторинга состояния улья с передачей данных через Telegram-бота или WiFi. Устройство обеспечивает контроль веса улья, температуры, влажности и состояния батареи с возможностью локального отображения данных на OLED-экране.

---

## 2. Основные функции системы

### 2.1. Сбор данных

**Процесс сбора:** пробуждение → снятие замеров → запись на MicroSD → параллельная отправка в Telegram-бот или через WiFi

- **Вес улья** — 4 тензодатчика по 20 кг (для теста — 50 кг), дельта датчика 50 грамм
- **Температура и влажность** — SHT30 размещается внутри улья, не в корпусе устройства; кабель до 1 метра от основного блока
- **Геолокация** — GPS, строго 1 раз в сутки (экономия энергии)
- **Напряжение батареи** — с конвертацией в % и расчётом оставшегося времени работы

#### GPS: логика поиска спутников

GPS-модуль (встроен в A7670E) работает в двух режимах старта:
- **Холодный старт** — первый запуск или после долгого простоя, занимает 1–3 минуты
- **Тёплый старт** — если данные об орбитах (almanac) сохранены, занимает 5–15 секунд

Поскольку GPS запускается 1 раз в сутки, каждый последующий запуск — тёплый. Последние известные координаты сохраняются в RTC-память ESP32 (переживает deep sleep) и на MicroSD как fallback — если сегодня не удалось получить fix, в телеметрию идут вчерашние координаты с флагом `"location_fresh": false`.

**Алгоритм GPS-сессии:**
1. Включить GPS-модуль (AT+CGNSPWR=1)
2. Ждать NMEA-данные максимум 3 минуты
3. Если fix получен — сохранить координаты, выключить GPS
4. Если за 3 минуты fix не получен — записать ошибку, использовать последние известные координаты, выключить GPS
5. GPS не мешает параллельной работе GSM (A7670E имеет отдельный приёмник)

### 2.2. Коммуникация

Два режима работы (две отдельные прошивки):

#### Режим GSM (основной, приоритет разработки)

**Транспорт — подробно:**

A7670E работает по 4G LTE (Cat-1), что обеспечивает стабильное соединение даже в сельской местности. Telegram API доступен исключительно через HTTPS (TLS 1.2). Схема работы:

1. **Настройка PDP-контекста** — AT-командами настраивается GPRS/LTE bearer с APN оператора (`AT+CGDCONT`, `AT+CGACT`). Это аналог "набора номера" для передачи данных.
2. **DNS-резолвинг** — модуль резолвит `api.telegram.org` → IP через встроенный DNS-клиент.
3. **TLS-сессия** — A7670E поддерживает TLS 1.2 нативно (`AT+CSSLCFG`, `AT+CHTTPSSTART`). Сертификат Telegram не нужно хранить на устройстве — используется режим без верификации CA (приемлемо для IoT в поле).
4. **HTTP GET polling** — устройство делает GET-запрос к `api.telegram.org/bot{TOKEN}/getUpdates?offset=...&timeout=30`. Telegram держит соединение 30 секунд (long polling) — если команда пришла, ответ приходит сразу; если нет — через 30 сек возвращается пустой ответ. Один запрос = одно 30-секундное окно ожидания команд.
5. **HTTP POST** — отправка телеметрии через `sendMessage` с JSON-текстом или через `sendDocument` для файлов.
6. **Закрытие соединения** — `AT+CHTTPSCLSE`, затем деактивация bearer.

Библиотека: **TinyGSM** управляет AT-командами; **ArduinoJson** формирует и парсит JSON; **UniversalTelegramBot** (или прямые HTTP-запросы) реализует логику бота.

**Логика GSM-сессии:**
- Включение модема (PWRKEY на IO4) → инициализация (много AT-команд, ~10–20 сек)
- Проверка сигнала (`AT+CSQ`) → если нет сигнала → записать неудачу → сон
- Отправка телеметрии (POST)
- Запуск long polling на 30 секунд (GET с timeout=30)
- Если команда пришла → обработать → ответить → сон
- Если 30 сек истекло без команд → сон
- В худшем случае команда ждёт следующего цикла пробуждения

#### Режим WiFi (альтернативный)

- Подключение к WiFi точке доступа (SSID/пароль в конфиге)
- Кнопка настройки (долгое нажатие) → ESP32 поднимает AP → веб-интерфейс для ввода SSID/пароля → сохранение в NVS Flash → таймаут 30 сек → выход из режима настройки
- Отправка телеметрии аналогично GSM-версии (HTTPS + Telegram API или HTTP на свой сервер)

### 2.3. Локальное отображение

**OLED-дисплей** (маленький, 0.96" или 1.3", уже приобретён) — выводит текущие показатели: вес, температуру, влажность, заряд батареи, время от RTC.

**Подключение дисплея:** дисплей монтируется снаружи корпуса устройства на кабеле до 1 метра. Используется интерфейс I²C — при правильно подобранных pull-up резисторах (4.7 кОм на SDA и SCL) I²C стабильно работает на расстоянии до 1 метра. Скорость I²C снижается до 100 kHz (standard mode) вместо 400 kHz — этого достаточно для обновления OLED. Никакой отдельной шины или специального кабеля не нужно — обычный 4-проводной кабель (VCC, GND, SDA, SCL).

**Вывода через внешний порт (UART/USB и т.п.) нет** — дисплей является единственным локальным интерфейсом вывода информации. Кнопки — единственный физический ввод.

**Кнопки управления:**
- **Кнопка 1 (активация экрана)** — одиночное нажатие → включить OLED на 30 секунд → погасить
- **Кнопка 2 (настройка WiFi)** — долгое нажатие (3+ сек) → войти в режим AP настройки (только в WiFi-прошивке; в GSM-прошивке — зарезервировано)
- **Кнопка 3 (сброс, опционально)** — аппаратный перезапуск ESP32

---

### 2.4. Энергоэффективность

- **GSM-модуль:** включается только на время отправки + 30-секундное окно; немедленный переход в сон при отсутствии активности
- **WiFi-модуль:** работа по расписанию, после сеанса — выключение
- **Глубокий сон (Deep Sleep)** между циклами — ESP32 потребляет ~10–20 мкА
- **Оценочная автономность:** ~14 суток от 1S2P 7 Ач при цикле раз в час
- **RTC DS3231** остаётся активным во время deep sleep и даёт точное время для пробуждения и временны́х меток в данных

---

### 2.5. Хранение данных

- MicroSD карта (минимум 8 ГБ)
- Запись каждого цикла в CSV или JSON
- **Циклическая запись:** 90 дней данных; на 91-й день перезапись данных с 1-го дня
- **Буферизация:** до 10 последних неотправленных пакетов при отсутствии сигнала; отправка при восстановлении связи

---

### 2.6. Управление через Telegram-бота

**Команды:**
- `/status` — краткое состояние: вес, температура, влажность, батарея
- `/telemetry` — полная телеметрия в JSON
- `/notifications on/off` — включить/выключить автоматические уведомления
- `/location` — координаты улья (последние известные)
- `/schedule` — настройка расписания

**Настройка расписания:**

| Пример команды | Результат |
|---|---|
| `/schedule 09:00` | 1 раз в сутки в 9:00 |
| `/schedule 09:00 18:00` | 2 раза в сутки |
| `/schedule 06:00 14:00 22:00` | 3 раза в сутки |
| `/schedule every 1h` | каждый час (24 раза) |
| `/schedule every 30m` | каждые 30 минут (48 раз) |
| `/schedule show` | показать текущее расписание |

- Минимальный интервал между отправками: **15 минут**
- Максимум: **96 отправок в сутки**
- Расписание сохраняется в NVS Flash и переживает перезагрузку

## 5. Алгоритм работы

### Режим GSM:

1. Пробуждение по таймеру (расписание из NVS)
2. Включение датчиков
3. Сбор данных: вес, климат, батарея
4. Сбор GPS (только если прошли сутки с последнего fix)
5. Сохранение на MicroSD
6. Включение GSM-модуля (PWRKEY) → инициализация AT-командами (~10–20 сек)
7. Проверка сигнала → нет сигнала → записать неудачу → шаг 12
8. Отправка телеметрии (HTTPS POST → Telegram sendMessage)
9. Long polling 30 секунд (GET getUpdates?timeout=30)
10. Если команда пришла → обработать → ответить → шаг 11
11. Выключение GSM-модуля
12. Обновление OLED (если была нажата кнопка)
13. Deep sleep до следующего цикла

### Режим WiFi:

1. Пробуждение по таймеру
2. Включение датчиков
3. Сбор данных: вес, климат, батарея
4. Сохранение на MicroSD
5. Подключение к WiFi (таймаут 15 сек, при неудаче — сон)
6. Отправка телеметрии
7. Ожидание команд 30 сек
8. Отключение WiFi
9. Обновление OLED
10. Deep sleep

### Режим настройки WiFi (по кнопке):

1. Долгое нажатие (3+ сек) кнопки настройки
2. ESP32 поднимает AP (SSID: "BeeHive-Setup")
3. Пользователь подключается с телефона → открывает 192.168.4.1
4. Веб-форма: ввод SSID и пароля WiFi-сети
5. Сохранение в NVS Flash
6. Таймаут 30 сек без активности → выход из режима, возврат к основной логике
7. Или нажатие кнопки перезапуска → перезагрузка в WiFi-режиме

## 7. Работа с плохим сигналом

- **Предварительный выбор оператора** в точке установки (Orange, T-Mobile, Play, Plus)
- **Логика повторов:**
  - Первая попытка — немедленно
  - Неудача → повтор через 5 минут
  - Вторая неудача → следующий плановый цикл
  - Буфер до 10 неотправленных пакетов на MicroSD
- **Индикация:**
  - Уровень сигнала (dBm) в каждом пакете телеметрии
  - Счётчик `send_failures` в JSON
  - Уведомление в Telegram при восстановлении связи после серии сбоев
- **Опционально:** внешняя антенна GSM при плохом покрытии

## 8. План тестирования

1. Тест операторов в месте установки (замер CSQ каждого оператора)
2. Тест стабильности соединения (10–20 циклов отправки)
3. Выбор оператора с лучшим покрытием
4. При необходимости — внешняя антенна + повторный тест
5. Тест WiFi-режима (подключение, AP-настройка)
6. Тест работы DS3231: точность пробуждения, сохранение времени при отключении питания
7. Тест циклического сна: 24 часа без вмешательства, проверка логов на MicroSD
8. Тест буферизации: отключить GSM антенну → проверить накопление пакетов → восстановить → проверить отправку буфера
